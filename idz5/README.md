## Часть 1 - Установка и настройка
Был создан docker-compose для настройки ManticoreSearch:
```yml
services:
  manticore:
    image: manticoresearch/manticore:latest
    container_name: idz5_manticore
    restart: unless-stopped
    ports:
      - "127.0.0.1:9306:9306"
      - "127.0.0.1:9308:9308"
      - "127.0.0.1:9312:9312"
    volumes:
      - manticore_data:/var/lib/manticore
    ulimits:
        nproc: 65535
        nofile:
            soft: 65535
            hard: 65535
        memlock:
            soft: -1
            hard: -1

volumes:
  manticore_data:
```

Было назначено 3 порта для подключения к ManticoreSearch:
- `9306` - через этот порт подключаемся к ManticoreSearch через mysql
- `9308` - через этот порт отправляем HTTP запросы
- `9312` — бинарный протокол ManticoreSearch. Стандартный порт ManticoreSearch

1. Проверка подключения через HTTP API:

```bash
curl -s "http://localhost:9308/sql?mode=raw" -d "query=SHOW TABLES"
```

2. Проверка подключения через MySQL:

```bash
mysql -h 127.0.0.1 -P 9306
SHOW TABLES;
```

### Что делает `morphology='stem_enru'`
Включает стемминг для русского и английского языка, для полноты поиска. Стемминг приводит слова к общей основе, чтобы поиск находил товары, даже если пользователь введет слово не в той форме (телефон, телефоны, телефонов)

### Зачем нужен `min_word_len`
Чтобы ManticoreSearch индексировал слова длиной от 2 символов, если короче этого значения, то слово не попадет в полнотекстовый поиск.

ManticoreSearch заранее подготавливает данные для быстрого поиска. Он разбивает текст на слова и запоминает где они встречались. При запросе он не читает все подряд, а смотрит свой индекс и находит, в нашем случае, подходящие товары по индексам.

### Зачем нужен `html_strip`
`html_strip='1'` говорит ManticoreSearch удалять HTML-теги из текстовых полей.

Например, если описание товара выглядит как HTML код:

```html
<p>Wireless headphones with <b>noise cancelling</b></p>
```
то в индекс попадет `Wireless headphones with noise cancelling`

### Чем RT-индекс отличается от plain-индекса

- Plain-индекс строится заранее из внешнего источника. Например если данные поменяются, то нужно заново перестраивать индекс. Больше подходит для данных, которые редко меняются или обновляются по расписанию. Подходит для архива новостей.
- Real-time индекс - это изменяемая таблица. В него можно добавлять, изменять, удалять  данные. Предназначен для изменений в реальном времени. Подходит как раз для католога товаров, доски объявлений.

## Часть 4 - Полнотекстовый поиск
Были выполненные поисковые запросы по индексу `products`

### 4.1 - Базовый поиск
Поиск по словам `wireless bluetooth headphones`

Используем функцию `MATCH()`, которая работает как поисковая строка. Она ищет не точное значение в колонке, а слова внутри полей

`WEIGHT()` показывает вес релевантности найденного товара. Чем выше вес тем выше товар в поисковой выдаче.

Запрос выполнился за 0.004 сек

### 4.2 - Поиск с точной фразой
Для поиска точной фразы использовали `MATCH('"noise cancelling"')`. Двойные кавычки говорят, что слова должны идти рядом и в указанном порядке

Запрос выполнился за 0.004 сек

### 4.3 - Поиск с оператором proximity
Использовался запрос `MATCH('"portable speaker"~3')`

Тут мы ищем товары где слова portable и speakers находятся близко друг к другу, а число `3` задает допустимое расстояние между словами

Запрос выполнился за 0.003 сек

### 4.4 - Поиск с фильтрацией по атрибутам
Для поиска с фильтрацией использовали `MATCH('laptop') AND price BETWEEN 30000 AND 80000 AND rating >= 4.0`.

То есть сначала искали товары со словом laptop, а потом урезали результаты по цене и рейтингу

Запрос выполнился за 0.005 сек

### 4.5 - Поиск по JSON-атрибуту

Здесь использовали фильтр по JSON полю: `tags.color`

Запрос выполнился за 0.013 сек

Он ищет товары по слову `gaming` и возвращает их, после он показывает как эти найденные товары распределяются по фильтрам (у нас по категориям и брендам) отдельными таблицами

Результаты в `checks/facets.txt`

То есть схема такая:
```txt
найденные товары
+
сколько товаров в каждой категории
+
сколько товаров у каждого бренда
```

В e-commerce это выглядит так:

1. Пользователь вводит необходимый ему товар. -> получает список товаров
2. Далее фасетный поиск строит фильтры в каталоге товаров и считает распределение результатов по разным фильтрам (сколько товаров X бренда, сколько товаров в наличии и тд)
3. Далее пользователь может сократить свой поиск выбрав эти фильтры.

## Часть 6 - Сравнение с PostgreSQL

Добавили отдельный контейнер для PostgreSQL в `docker-compose.yml`.  Сгенерировали набор данных той же структуры и объема, что и для ManticoreSearch.

Скрипт генерации в `scripts/generate_pg_products_csv.py`

PostgreSQL была создана таблица `pg_products` с 100000 товарами. Для полнотекстового поиска использовали `tsvector` и `GIN-индекс`. `tsvector` хранит не обычный текст, а уже подготовленную версию текста для поиска. При помощи него PostgreSQL разбивает текст на слова, убирает лишние слова, приводит слово к базовой форме и запоминает позиции слов.

А GIN-индекс заранее хранит, какие слова в каких строках встречаются, за счет него поиск происходит быстрее, так как PostgreSQL не читает всю таблицу подряд, а смотри в `GIN-индекс`.

`ManticoreSearch` выполнил поиск за 11 мс, а `PostgreSQL` за 39 мс

Результаты сравнения находятся в `checks/pg_vs_manticore.txt`

### Сравнительная таблица ManticoreSeearch и PostgreSQL

| Характеристика | ManticoreSearch | PostgreSQL (tsvector) |
|----------------|-----------------|------------------------|
| Время поиска (100K docs) | 11 мс | 39 мс |
| Релевантность (BM25 vs ts_rank) | 6559 | 0.69424576 |
| Морфология из коробки | `morphology='stem_enru'` | `to_tsvector()` - обрабатывает текст в таблице, `to_tsquery()` - обрабатывает поисковую фразу |
| Фасетный поиск | Встроенный | Можно реализовать через группировку `GROUP BY` |
| JSON-атрибуты | есть JSON-атрибуты, можно через них фильтровать (`tags.color = 'black'`) | тоже есть, хранятся через тип данных `JSONB`, тоже можно фильтровать (`tags->>'color' = 'black'`) |
| Транзакции | нет | да |
| Когда использовать | Поиск по каталогу, фасеты, быстрые фильтры | Транзакции, основное хранение данных |

## Часть 7 - Обновление и удаление

Были выполнены операции изменения данных в Real-time индексе `products`

### UPDATE

Изменили цену и рейтинг товара с id = 1

```sql

SET price = 9999.99, rating = 4.9
WHERE id = 1;
```

После выполнения запроса, проверили через SELECT -> цена и рейтинг изменились.

### DELETE

Операция DELETE использовалась для удаления товара с id = 2

```sql
DELETE FROM products
WHERE id = 2;
```

После удаления проверили через SELECT -> запрос не вернул строк, значит удаление прошло успешно

### REPLACE

REPLACE использовался для полной замены товара

```sql
REPLACE INTO products (
    id,
    title,
    description,
    category,
    brand,
    price,
    rating,
    reviews_count,
    in_stock,
    tags,
    created_at
)
VALUES (
    3,
    'Demo replaced black phone',
    'This document was fully replaced with REPLACE operation. Black phone with fast charging and updated description.',
    'phones',
    'DemoBrand',
    55555.55,
    4.8,
    777,
    1,
    '{"color":"black","source":"replace_demo","condition":"new"}',
    1710000000
);
```

REPLACE заменяет товар целиком, в отличии от UPDATE, который меняет отдельные поля

Результаты выполнения запросов в `checks/update_delete.txt`

### Разница UPDATE в Manticore и PostgreSQL

В PostgreSQL `UPDATE` выполняется в рамках полноценных транзакций. PostgreSQL гарантирует согласованность данных (изменения либо полностью применятся, либо нет. Данные не будут в полуобновленном состоянии).

В Manticore `UPDATE` используется для быстрого обновления данных. Изменение может примениться на одном узле, а до других дойти может чуть позже.
